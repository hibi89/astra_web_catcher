## A. 첨부 이미지 1 — `개발방향..PNG` : 원문 전사

>
> 그러면 설계 원칙도 이렇게 잡자:
>
> **참고 사이트에서는 기능·사용 흐름을 배우고, 데이터 구조는 네가 가진 것을 기준으로 연결한다.**
>
> `원본 기능 관찰 → 네 DB·API 구조와 매핑 → 부족한 항목 확인 → 구현 → 실제 데이터로 테스트`
>
> 이때 AI가 기존 DB를 마음대로 바꾸면 안 되고, 없는 필드·다른 계산 기준은 먼저 알려주고 변경 승인을 받아야 해. 연결 테스트도 원본 데이터 대신 복사본이나 테스트 DB부터 하고.
>
> 이 방향이면 단순 사이트 복제가 아니라, 네 데이터를 쓸 만한 서비스로 만드는 개발 보조도구가 되는 거야. 최종 비교도 화면뿐 아니라 데이터 정확성·사용성·수정 시간까지 보자.

## E. 이 설계의 변경 불가 원칙 (원문에 근거한 실행 체크)

1. 목적은 참고 사이트 그 자체의 복제가 아니라 **사용자의 데이터를 연결하는 사용 가능한 웹서비스/대시보드 제작 보조**.
2. 입력: **참고 URL + 사용자 수동 시연/화면 자료 + 대상 프로젝트의 DB/API 구조**.
3. 출력: **관찰 근거가 있는 기능 명세 + 사용자 DB/API에 맞춘 독립 구현 + 테스트 근거**.
4. 확인된 기능과 미확인 기능, 추측한 계산식을 분리하고, 미확인은 사실인 것처럼 구현·보고하지 않는다.
5. 기존 DB·필드·산식·권한·코딩 규칙을 임의 변경하지 않는다. 부족한 필드나 다른 계산 기준은 사용자에게 알리고 승인받는다.
6. 테스트는 **원본 데이터 대신 복사본/별도 테스트 DB** 우선. 원본 서비스·계정·비밀정보 보호.
7. 처음 지원할 기능은 목록/검색/필터/상세/등록/수정/삭제/기본 집계. 결제·정산·복잡한 권한은 v1 범위 밖.
8. 현업 성공 판정은 UI 유사성만으로 하지 않고 **데이터 정확성·사용성·수정/검증 시간·기존 시스템 호환성·안전한 재사용**으로 한다.
9. 원본 서버의 비공개 코드 추출이나 접근 제한 우회가 목적이 아니다.
